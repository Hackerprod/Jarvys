# Inline chat blocks

Assistant Markdown fences are dispatched by the language-to-renderer registry in `InlineBlockRenderers.kt`. SVG, chart, and LaTeX blocks draw natively in Compose. Assistant GFM tables wrap full cell text, divide the available width in proportion to measured column content, and scroll horizontally only when an unbreakable cell run needs more width than the message area. User-message tables and Markdown rendered outside assistant replies keep the library renderer. Invalid or unfinished final special fences fall back to copyable code.

## Scroll re-entry

A Robolectric Compose measurement of a completed 2,240 px assistant reply with 36 paragraphs, a list, SVG, and chart confirmed that LazyColumn disposed the row offscreen and recreated it on return. Before the cache fix, loading callbacks increased from 1 to 2 and row-height samples changed from 2,240 px to 0 and back to 2,240 px. SVG and chart parse/mount counts each increased from 1 to 2. With a requested anchor at index 0 / offset 180 px, the list returned at index 3 / offset 16 px and stayed there across three frames; while the row was offscreen it was at index 19 / offset 10 px.

The empty frame came from the Markdown renderer's asynchronous parse: the row-local remembered state was discarded with the LazyColumn item, so re-entry showed its empty loading slot until parsing completed. Recreated inline blocks also parse and mount again, adding synchronous work, but their measurements did not cause the zero-height sample. The list anchor shift followed the temporary row collapse.

`ChatMessageList` owns a successful Markdown-state cache for its `conversationKey` lifetime. Assistant Markdown always calls `rememberMarkdownState(normalizedMarkdown)` and renders through one stable `Markdown(...)` call, whether the text is cached, parsing, or streaming. A text edit replaces the parser state while leaving the Markdown call and its last-success holder mounted. The displayed state follows this order: newly parsed `Success`, newly parsed `Error`, exact-text cached `Success`, the last displayed `Success` while replacement text parses, then the parser's current state. If a new parse produces a `Success` with the same content as the cached or last displayed tree, the existing `State.Success` instance is reused to keep the Markdown subtree mounted. Only completed, non-streaming parsed successes enter the cache; streaming skips cache reads and writes. Parsing stays on the renderer's asynchronous path, and SVG sanitization and inline rendering semantics are unchanged.

The cache is keyed by Markdown content and retains each successful version until its conversation closes. A translated message, an edited response, the original text, and tool-detail variants can therefore remain as separate entries during that conversation. This lifetime is acceptable because it avoids an artificial eviction cutoff and the cache is released with the conversation's `ChatMessageList`. The re-entry test checks that the loading count stays unchanged, the 2,240 px row height and list anchor are restored without an empty-height frame, and recreated SVG/chart blocks do not cause the measured scroll shift. Additional Compose coverage checks that changing text after a cached re-entry keeps the prior tree visible while parsing, and that same-text recomposition does not remount a cached inline block.

## Interim updates visibility

Main chat's model-turn preambles are ordinary assistant rows with stage `PROGRESS`. The pre-fix Compose reproduction showed this sequence: provider text deltas created a visible `assistant_stream`; when the reply included tool calls, `CoreAgentLoop` invoked `assistantTextStreamEnded` and `AgentRunUiState` removed that row; it persisted the model tool-call batch with `assistantProgress=true` and emitted `assistantProgress`; the service reread the batch as an assistant/`PROGRESS` event; `ConversationVisibility` filtered that event; then tool results and a later, separate final assistant answer appeared. The pre-fix test passed by observing the streamed text before tool promotion and its absence afterward. The callbacks now publish the durable preamble while the stream row still exists. `AgentRunUiState` replaces that row in place and transfers its `timelineKey`, then the subsequent stream-ended callback has nothing to remove. Reusing a CoreAgentLoop run ID on later tool turns creates a fresh stream key after each promotion.

When a persisted timeline refresh arrives before the progress callback, it matches the in-flight stream to a later `PROGRESS` row owned by the same user turn, transfers the key during reconciliation, and removes the duplicate stream row. Reopening history projects the persisted preamble at its model tool-call sequence, before tool results and the final assistant message. For unresolved tool batches, the existing pending-tool row keeps its preamble detail together with the recovery evidence, preserving the batch's single physical timeline sequence. Only the main chat opts into `PROGRESS` projection; the default remains hidden for workspace and Crew timelines, where interim updates are not enabled.

The changed visibility assertions are scoped to that choice: `ConversationVisibilityTest` now checks that the default projection still hides progress and that main chat opts in, while `ConversationVisibilityUiTest` checks that the same live row remains visible after tool-call promotion and final completion. `ConversationReaderDatabaseTest` verifies the reopened order and single persisted preamble. Progress rows remain outside the final-answer path: only stage-less assistant rows qualify as the latest answer for regeneration, progress carries its owning user-message ID for delete/regeneration invalidation, and stage-bearing rows do not expose the final-answer action footer. Existing title, context, and compaction inputs continue to come from their message/transcript records, so showing the row does not create a second assistant answer or alter model context.

These measurements confirm `strokeWidth` scaling, default 3 x 3 marker dimensions, `viewBox` transforms, `refX/refY`, `orient=auto`, explicit CSS marker styles, and line/path/polyline references for the tested samples. AndroidSVG 1.4 does not support `auto-start-reverse`, `context-stroke`, or `context-fill`; the observed outcomes are render rejection or unsupported-paint defaults. These are measured library limits; this document makes no claim that they are being fixed.

The owner's real OMEGA SVG uses `<marker markerWidth="10" markerHeight="10" refX="8" refY="5" orient="auto">` with no `markerUnits` or marker `viewBox`, on a path with `stroke-width="2.5"`. SVG's default is `markerUnits="strokeWidth"`, so the 10-unit head scales to 25 viewBox units. Chromium draws the same head size. With `markerUnits="userSpaceOnUse"`, it measures 10 units, 2.5 times smaller. `OmegaSvgRenderingTest` keeps this behavior with API 34 native rendering and pixel measurements of approximately 25 and 10 viewBox units.

For inline arrows, give the SVG a `viewBox` and explicit marker dimensions and reference points. The default `markerUnits="strokeWidth"` ties the head size to the line; use `userSpaceOnUse` and a marker `viewBox` for a fixed head size. Use `orient="auto"`, `fill="currentColor"` for a filled head, or `fill="none"` with `stroke="currentColor"` for an outline. Keep labels legible on portrait phones and sized to fit their shapes.

## Prompt guidance

`VISUAL RESPONSES` says that chat renders `svg`, `chart`, and `latex` fences inline. It asks for a compact figure right after the sentence it illustrates when a structure, flow, spatial layout, or magnitude comparison is clearer visually, with a text explanation; prose and tables handle other content. It specifies the chart JSON shape and data provenance, `viewBox`, a transparent background, `currentColor`, the 25-unit default OMEGA marker example, fixed-size marker guidance, LaTeX fences, and module tools for files such as PPTX or PNG.

The five-box diagram case adds two authoring rules: `marker-end` appears only at a complete path's final endpoint and `marker-start` only at its initial endpoint, so draw each arrow as its own `<line>` or `<path>`. SVG text does not wrap or clip automatically; labels wider than their boxes overflow. Compare label character count with box width at the chosen font size. For 4+ steps on a portrait phone, prefer a vertical flow, two rows, or short labels, and keep all content inside the `viewBox`.
