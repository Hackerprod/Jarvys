# Flujo de carga de skills: Jarvys y OpenClaw

## OpenClaw actual

Referencia examinada: `openclaw/openclaw` en `main`, commit `3635488e5a325562f1f57f17a32a77fbda63d4a3` (2026-10-18).

| Etapa | OpenClaw actual | Contraste inicial con el caso de Jarvys |
| --- | --- | --- |
| Descubrimiento | El prompt muestra un catálogo `<available_skills>` con nombre, descripción y ubicación. La sección de skills pide escanear las descripciones, leer un match claro y no leer ninguna si no hay match. | El caso real muestra que el modelo ya tenía una instrucción de carga selectiva, pero leyó 11 referencias distintas de un mismo bundle en tres tandas. |
| Selección inicial | Si el `skills_search` está disponible, el prompt orienta a buscar por objetivo y términos distintivos. Si hay varios matches, elegir el más específico. El prompt dice `Up-front max one`; esta regla limita la selección inicial, no impide leer más adelante otra instrucción que el flujo activo requiera. | La guía actual no consiguió que el modelo esperara a comprender el proyecto antes de cargar muchas referencias. La conducta observada es una ráfaga de referencias distintas, no repetición del mismo cuerpo. |
| Carga del cuerpo | El catálogo contiene metadatos, no los cuerpos completos de `SKILL.md`. El modelo lee el archivo de la skill elegida con la herramienta `read`; `skills_read` también lee una skill por nombre exacto. | Jarvys expone un manifest con 14 recursos versionados y `read_skill` acepta una referencia por llamada. En el caso se cargaron 11 recursos distintos por adelantado. |
| Control mecánico e idempotencia | `read` deduplica una ruta de instrucción ya servida en el contexto del modelo, incluso si las llamadas son concurrentes; responde que reutilice el contenido. La caché se vacía cuando la compacción reemplaza el contexto, para que se pueda volver a servir el archivo. No se observa un límite mecánico por respuesta para rutas distintas. | Deduplicar una referencia idéntica no resolvería la ráfaga de Jarvys porque cada llamada exitosa del caso apuntaba a un recurso distinto. Una barrera por turno de una referencia sería un control adicional al modelo y no una mecánica equivalente de OpenClaw. |
| Límites y acceso | El catálogo se limita por cantidad y caracteres configurables (por defecto, 150 skills y 18.000 caracteres); al exceder el presupuesto, acorta descripciones y luego omite entradas. Las allowlists por agente determinan las skills elegibles. Estos límites reducen metadatos en el prompt, no la cantidad de lecturas distintas que el modelo puede solicitar después. | El problema reportado no es que el catálogo de metadatos sea grande: son ~49,4 KB de referencias completas leídas antes de inspeccionar la tarea, más tres fallos. |
| Poda de resultados | En este `main` no existe la ruta antigua `src/agents/pi-extensions/context-pruning`. Sí hay truncación genérica de resultados de herramientas; no encontré una excepción específica para skills en esos componentes. Al reemplazarse el contexto, la caché de entrega de instrucciones se invalida y permite volver a leerlas. | Proteger los resultados de skill contra cualquier poda no es una característica que deba atribuirse a OpenClaw actual. La conducta comprobable es evitar duplicados mientras el cuerpo siga en el contexto y volver a servirlo tras compacción. |

- El commit [`b621d4550beb559bc65f622cf75d2cc81387a64c`](https://github.com/openclaw/openclaw/commit/b621d4550beb559bc65f622cf75d2cc81387a64c) (`2026-01-18`, `chore: tighten skills prompt rules`) incorporó el prompt “Skills (mandatory)” y las reglas de elegir antes de leer y no leer más de una skill *up front*.
- El commit [`e87fcb0850697e747e1c73f414aabe4bd6155531`](https://github.com/openclaw/openclaw/commit/e87fcb0850697e747e1c73f414aabe4bd6155531), integrado como [PR #130286](https://github.com/openclaw/openclaw/pull/130286), añadió idempotencia por ruta y lecturas completas de `SKILL.md`. Es una reparación de lecturas repetidas de la misma ruta, no un tope para una serie de recursos diferentes.
- Las propuestas de catálogo lazy [#29267](https://github.com/openclaw/openclaw/issues/29267) y de índice lazy por escenario [#89361](https://github.com/openclaw/openclaw/issues/89361) están cerradas. El `main` examinado todavía incluye un catálogo de metadata acotado en el prompt.
- El [issue #143155](https://github.com/openclaw/openclaw/issues/143155) y el [PR abierto #143229](https://github.com/openclaw/openclaw/pull/143229) documentan una tensión distinta: workflows que requieren gates en varias skills pueden chocar con “up-front max one”. El cambio propuesto permite leer otra skill cuando el workflow activo lo requiera; no impone ni recomienda leer varias de antemano.

**Conclusión del referente:** no encontré un issue, PR o changelog de OpenClaw que afirme resolver una ráfaga de lecturas de referencias distintas. El referente respalda seleccionar una skill antes de leerla mediante el prompt y deduplicar mecánicamente repeticiones de la misma ruta; no respalda un límite global de una lectura distinta por respuesta del modelo.

La corrección de Jarvys de procesar una referencia de `read_skill` por respuesta del modelo es, por tanto, una barrera de flujo adicional; no debe describirse como una mecánica ya existente en OpenClaw. La verificación histórica de `b621d455` se hizo consultando el endpoint de commits de GitHub (`GET /repos/openclaw/openclaw/commits/b621d4550beb`) y comprobando el SHA completo, fecha, asunto y diff del archivo: el clon local era `--depth 1` y no contenía ese ancestro en `git log`.

## Jarvys antes del cambio

| Etapa | Flujo anterior | Efecto observado |
| --- | --- | --- |
| Catálogo y selección | Coding recibía el core y el catálogo de la guía Factory; el prompt solo decía que cargara orientación relevante. Crew ensamblaba una indicación equivalente y `CodingAgentInstructions` pedía cargar skills relevantes, pero ninguno describía el procedimiento de seleccionar, inspeccionar el estado del proyecto y pedir una referencia cuando el paso la necesitara. | Una instrucción general de “solo lo relevante” no impidió que el modelo solicitara referencias distintas en lotes grandes. |
| Admisión de llamadas | Una respuesta del modelo entrega `reply.calls` como un lote a `CoreAgentLoop`. `LoadSkillTool.executionMode() == SEQUENTIAL` ejecuta en orden las llamadas del lote; no fuerza una nueva respuesta del modelo entre ellas. No había política de admisión por respuesta. | Las 7, 3 y 4 llamadas del caso se ejecutaron en sus tres lotes, en vez de que el modelo inspeccionara cada resultado antes de pedir la siguiente referencia. |
| Bundle y presupuesto | `factory-guidance-v90` ofrece 14 referencias. El core parseado ocupa 5.087 bytes; las referencias suman 65.532 bytes frente al máximo de 65.536; core, referencia individual y total tienen máximos de 8.192, 16.384 y 65.536 bytes. En Coding el contrato vigente del core indica lectura bajo demanda, pero los resultados completos se entregan uno por uno dentro del lote; Crew admite resultados completos sin presupuesto por turno. | Los cuerpos eran 11 recursos válidos y distintos, no una misma skill reinyectada 11 veces. Por ello, una deduplicación por referencia idéntica no habría resuelto la ráfaga. |
| Idempotencia y poda | `read_skill` no reconocía que el resultado completo exacto siguiera visible. La compactación puede conservar, truncar o retirar resultados; no existía una decisión de repetición vinculada al transcript concreto que se envía al modelo. | Las lecturas repetidas de una misma referencia podían gastar salida de nuevo, y no había base segura para reutilizar resultados parciales. |
| Errores históricos | Cuando el par `resource`/`resource_version` no correspondía al bundle actual, `LoadSkillTool` devolvía `Unknown or unavailable skill resource/version`. La actividad Crew guarda estado y presentación (`ToolActivity`), no los argumentos de la llamada. | El texto de las tres actividades confirma un fallo de validación de recurso/versión, pero la tabla `crew_message_activities` aportada no permite reconstruir los argumentos enviados. No se atribuye a esas tres llamadas una pareja de valores que no consta en la evidencia. |
| Presentación | `activitySkillName` mostraba el nombre de la skill sin el identificador de referencia. | La interfaz agrupaba visualmente lecturas diferentes como `Loaded skill · APK Factory`. |

La ruta de ejecución y el criterio de fallo están en `CoreAgentLoop.java` (construcción y ejecución de `reply.calls`) y `LoadSkillTool.java` (validación contra `FactoryGuidanceBundle.version` y sus resource IDs). `CrewCheckpointStore.java` serializa los argumentos sanitizados de turnos `TOOL_CALLS` en un checkpoint de Crew (`encodeLoop`, cerca de las líneas 668–675); esos argumentos podrían aclarar una ejecución concreta si se aporta su checkpoint. No están en las filas de actividad de esta misión ni en este worktree, y no se consultó el teléfono ni se usó ADB. El test nuevo reproduce el bucle real con tres pares inválidos representativos, pero no los presenta como los argumentos históricos.

## Diseño aplicado

- **Selección en el prompt:** el prompt de Coding y el prompt dinámico de Crew indican escanear el catálogo, elegir la skill más específica, leer solo lo necesario para el paso actual y hacerlo de una en una después de inspeccionar el resultado. `MainAgentPrompt` no cambia y su límite de 7.600 caracteres permanece intacto.
- **Admisión real en el bucle:** `CoreTool` declara `ResponseCallPolicy` con `MULTIPLE_PER_RESPONSE` como valor existente por defecto y una opción `ONE_PER_RESPONSE`. `CoreAgentLoop` aplica la política declarada por cada instancia de herramienta; no contiene nombres, IDs ni excepciones de APK Factory. `LoadSkillTool` usa la opción de una lectura por respuesta para cualquier skill con la que trabaje. Las llamadas posteriores reciben resultados emparejados y estado `NEVER_LAUNCHED`/`tool_not_started`, en orden; no se contabilizan como ejecuciones o fallos. La primera llamada consume el paso incluso si su lectura falla. Las demás herramientas de la misma respuesta continúan su flujo habitual.
- **Idempotencia por contenido visible:** el bucle pregunta a la herramienta por una identidad estable y verifica que un resultado completo exacto siga en el transcript enviado a esa respuesta. Un resultado truncado, omitido o quitado por compactación no es reutilizable y deja que se lea otra vez. No se fija un cuerpo fuera del contexto que el modelo recibió.
- **Errores y actividad:** el error de catálogo enumera la versión actual y los resource IDs válidos; el error por tipos incompatibles también aporta ese catálogo cuando el ID de skill está disponible. La actividad de una skill visible incluye el recurso, por ejemplo `Loaded skill · APK Factory · database`. Skills marcadas internas siguen usando las etiquetas genéricas y no exponen nombre, referencia ni detalle.
- **Tamaño del bundle:** no se cambió el core, el manifiesto, los hashes ni la versión del bundle. El core ya ofrece el catálogo y las reglas generales; cargar automáticamente las referencias `basics` y `lifecycle` sería incompatible con el margen actual del paquete y no corrige la admisión de lotes. `FactoryGuidanceBundleTest` conserva los límites y hashes existentes.

La barrera de una referencia por respuesta es una regla de flujo local, respaldada por el fallo de admisión mostrado arriba. OpenClaw respalda las instrucciones de selección previa y la idempotencia de rutas repetidas, pero no contiene una barrera equivalente para varias referencias distintas en la misma respuesta. No se introduce un tope numérico global de lecturas por misión.

## Reproducción integrada y comprobaciones

`ApkFactorySkillScopeTest.realCoreAgentLoopAdmitsOneSkillReferencePerResponseAndReportsBaselineBurstCost` ejecuta el `CoreAgentLoop` real con `LoadSkillTool` y el bundle v90 del proyecto. El modelo doble reproduce las tres ráfagas (7 + 3 + 4 llamadas). El modo anterior se compara revirtiendo solo la política de admisión de la herramienta; no se simula la lógica del loop.

| Medida | Baseline sin política por respuesta | Flujo progresivo | Diferencia |
| --- | ---: | ---: | ---: |
| Resultados completos enviados al modelo, incluidos encabezados | 49.399 caracteres | 16.676 caracteres | −32.723 (−66,2 %) |
| Cuerpos de referencia, sin encabezados | 48.568 caracteres | 16.444 caracteres | −32.124 (−66,1 %) |
| Recursos válidos cargados | 11 | 3 | 8 menos |
| Errores de lectura en las tres llamadas inválidas del fixture | 3 | 0 | No iniciadas bajo la regla de flujo |
| Llamadas marcadas `tool_not_started` | 0 | 11 | 11 explícitas |

Los 3 pares inválidos del fixture incluyen un recurso inexistente y versiones no actuales; reproducen el tipo de fallo documentado, no los argumentos exactos de la misión del teléfono. El segundo test integrado verifica que un `resource` de tipo incorrecto también devuelve versión y catálogo actuales.

La cobertura añadida comprueba además la política genérica y el orden de resultados con herramientas hermanas; que un primer fallo consume el paso; la reutilización solo cuando el resultado completo está en el transcript; que truncar o compactar permite volver a leer; las instrucciones de Coding y Crew; la etiqueta visible con referencia; y el anonimato de actividades internas. `FactoryGuidanceBundleTest` y los tests dirigidos de actividad completan la verificación del contrato del bundle y la UI. No se cambia Room ni se requiere emulador.

La compilación Java/Kotlin de PlayDebug ocurrió como dependencia de `:app:testPlayDebugUnitTest`. La selección focal final pasó **56/56 tests**; después de conservar el texto original de HTML y publicación, `originalCodingV3PromptIsCompleteScopedAndAbsentFromCaptainCatalog` pasó también en una verificación focal adicional (**1/1**). En una selección más amplia anterior aparecieron además `preFactoryVersionOneMigratesWithoutBeingRelabeledOrAutomaticallyResumed`, el fallo conocido de persistencia/`AtomicFile` en Windows, y `explicitSpawnSelectionDropsUnusableSkillsWithoutExpandingTools`, cuya aserción de ausencia de `read_skill` no pertenece a las rutas de admisión modificadas; ambos se dejaron fuera del filtro final. No se empaquetó un APK.
