# Agent messaging: current behavior and unified design

Status: implementation and verification notes are reconciled below. The `conversation_items`, `messages`, and existing workspace/crew tables remain the durable stores; no Room schema migration is part of this change.

## 1. Goal and constraints

An accepted message between agents must become a durable, ordered input in the recipient's conversation. If that agent is running, the content joins its transcript at the next model boundary. If it is idle, waiting, blocked, or finished, the same content starts a model turn through that recipient's normal turn runner. Each input has a stable identity and an incorporation acknowledgement, survives a process restart, and is delivered once.

The conversation transcript has one input value with an explicit origin (`USER`, `AGENT`, or `SYSTEM`), typed provenance, and the original content. Agent-originated content is model input and internal evidence, never a user message or an assistant answer. In the in-memory transcript, internal input turns can use the assistant storage role for compatibility; consumers that need authorship use origin/provenance, and compaction renders them as `[agent_input ...]` with source and trust. The screen projection excludes communication inputs by origin; only the assistant's answer and the normal tool activity are visible. STOP cancels the active run generation; it does not own later or still-pending agent input identities.

Hard constraints:

- Keep the published Room schema unchanged. Persist through the existing conversation ledger/message rows and existing workspace/crew rows and receipts.
- Keep workspace control ownership, native `CORRECT`, revision checks, and existing approval/policy gates authoritative.
- No synthetic “please inspect inbox” prompt, wake carrying only a reference, checkpoint polling as delivery, per-tool/workspace hardcodes, or invented numeric loop limit.
- Do not display AGENT/SYSTEM communication as a user bubble, assistant bubble, workspace chat card, or technical card. Exclude it generically by origin.
- Agent content is untrusted source text. Its provenance does not grant user authority or authorize tools or approvals.

Main-chat genuine-user steering currently bypasses that metadata (`CoreAgentLoop.java:218-220,1389-1395`).

## 3. Worker/workspace baseline before this change

- `crew_send`, `msg_send`, `ask_chief`, and `report_done` are separate Crew operations (`crew/CrewTools.java:34-40,71-111`). `CrewMessageBus` appends to an in-memory log and per-recipient mailbox and notifies waiters; checkpoint code persists/restores its pending messages (`crew/CrewMessageBus.java:12-40,64-68,91-112,133-165`; `crew/CrewManager.java:653-710`).
- A running bot's `takeDurableMessages` polls the bus at loop/checkpoint boundaries. `CoreAgentLoop` appends real content as an `IncomingMetadata` message and deduplicates by incoming IDs, but the current `appendIncoming` represents non-user agent messages with provider role `user` (`crew/CrewManager.java:1099-1146`; `CoreAgentLoop.java:1364-1449,1476-1480`). The message is not offered to an in-flight model request; `enqueueFresh` only wakes bus waiters. Thus a direct Jarvys message can wait until a checkpoint.
- `WorkspaceCoordinator.enqueueNativeControl` persists native control and routes it through `WorkspaceControlOwners`, preserving the native UI origin, assignment/revision binding, STOP ownership, and `CORRECT` rules (`MainActivity.kt:1170`; `workspaces/WorkspaceCoordinator.kt:192-232,235-311`; `workspaces/WorkspaceControlOwners.kt:5-26`). `CORRECT` either resumes the exact recoverable cycle or dispatches a user correction into a live/quiescent bot (`WorkspaceCoordinator.kt:276-290`). This control path is a human control plane and must remain distinct from agent-authored content.
- `WorkspaceInputIncorporationDelivery` writes an idempotent receipt only after it finds a checkpoint that proves the exact payload was incorporated (`WorkspaceInputIncorporationDelivery.kt:8-12,59-139`). A receipt means durable transcript incorporation, not understanding or action (`WorkspaceCoordinationDelivery.kt:244-277`). `WorkspaceCoordinationDelivery` reconciles evidence and receipts; it does not start a model turn (`WorkspaceCoordinationDelivery.kt:10,311-320`).
- Worker states are `RUNNING`, `WAITING`, `DONE`, `STOPPED`, `FAILED`, `PARTIAL`, and interrupted/requires-explicit-resume states (`crew/CrewManager.java:38-46,285-291,1493-1560`). Normal messages received while running/waiting are stored for later polling; DONE starts a new cycle; stopped/failed/partial require explicit resume, while interrupted recovery is guarded by checkpoint and owner rules. An incoming conversation message must be admitted through this state/ownership model, not by bypassing it.

## 6. Delivered unified design

### 6.1 One typed conversation input

Use a single internal value with `origin = USER | AGENT | SYSTEM`, `content`, durable `messageId`, and provenance for non-user input: `{sessionId, workspaceId, assignmentId, botId, messageId, kind, principalRole, correlationMessageId, referenceId, contentSha256, assignmentRevision, requestId, missionId, cycleId}`. Principal role is runtime-assigned `SUPERVISOR | SUBORDINATE | PEER`; missing or invalid legacy values fail closed to PEER. The typed value is shared by both directions; recipient session identity is resolved from the admitted workspace/assignment and validated owner, not a tool/workspace hardcode.

`USER` remains backed by the existing user row. `AGENT` and `SYSTEM` are first-class roles in the existing `messages.role` text column, with content in `message_parts` and provenance encoded using an existing typed message-part payload. The existing `conversation_items` sequence is the ordering spine; the existing `messages.stable_id` unique index is the durable idempotency key. No entity/table/column/index migration is needed. Reusing `ROLE_USER` for these inputs is prohibited because title, visibility, memory, steering, and regeneration infer authorship from it.

### 6.2 Provider representation

The transcript retains origin as typed metadata and the unmodified content. Provider adapters serialize AGENT as a provider `user` message with a provenance header rendered using the existing escaped, untrusted envelope pattern (`ConversationTurn.IncomingMetadata.render`), including `origin=AGENT`, source identity, kind, typed principal and `isUser=false`. This avoids assistant-prefill histories and keeps copied text from becoming the assistant's own words. The header wraps; it does not replace or paraphrase worker content. USER remains a normal `user` message. SYSTEM remains internal, never starts a turn, and is not promoted to a provider assistant message. Tool/approval authorization continues to come only from the existing policy and approval pipeline. `AgentProviderSerializationTest` exercises OpenRouter and Codex Responses serializers for a Central AGENT-started turn, the initial worker TASK, and steering between assistant steps; each payload begins and ends with `user` and contains no adjacent assistant turns.

### 6.3 Admission, ordering, steering, and acknowledgement

- A message is committed to the recipient's conversation before returning admission success. Its stable ID deduplicates an identical retry; a retry with changed provenance or body conflicts. The repository sequence, not wall-clock time, orders messages, including concurrent workers.
- The main service admits AGENT input through the same session lane, pending-input provider, `CoreAgentLoop` incorporation callback, checkpoint-before-ack, and `enqueueStoredMessageFollowUp`/`recoverPendingInputs` used by user content. The pending provider reads both USER and AGENT inputs but preserves origin; acknowledgements record incorporation by exact durable ID. Compaction preserves AGENT source, sender, type, principal role, correlation ID, and trust in an `[agent_input ...]` record, and uses only assistant-authored messages as assistant boundaries.
- Crew delivery admits through the recipient's existing conversation and turn owner. A running loop is signaled directly and consumes ordered durable inputs at its next safe model boundary; it does not query an inbox at checkpoints. An inactive/waiting bot gets a new turn. Workspace workers are spawned in a prepared state, bound to the exact durable assignment/revision, then started; this closes the race where a fast result could be sent before the assignment had a bot binding. A DONE assignment stays bound at the same revision; one answer to its exact unclaimed QUESTION/BLOCKER may start a follow-up cycle with the same mission restrictions. This is an AGENT input, not a native `CORRECT` control. Current assignment revision and `WorkspaceControlOwners` precedence are rechecked before dispatch. STOPPED/FAILED/PARTIAL/interrupted states retain their existing explicit-resume authority.
- Ack state distinguishes durable admission from model incorporation. `delivered` means the recipient conversation committed the exact ID. `incorporated` means that exact content and provenance reached the model transcript and its checkpoint was saved. If a supervisor outbox commit succeeds but Crew admission or its receipt fails, the tool reports `PENDING_DELIVERY`, with delivery unconfirmed; an exact retry or authorized resume reuses the same ID. Workspace receipts remain audit evidence and are written from the actual incorporation callback, not as a substitute for dispatch or as the only source of a later checkpoint observation. Diagnostic/model-reading tools may inspect these states; the screen does not project them.
- On service restart, scan pending inputs only for the Central execution session. Worker execution sessions are reconciled and resumed by their `CrewManager`, which owns each worker checkpoint and source-message delivery receipt. If a worker checkpoint already contains an input ID, acknowledge without appending it again. This closes the in-memory steering-queue recovery gap described by OpenClaw without asking the Central service to run a worker session.

### 6.4 STOP, ordering, concurrency, and loops

STOP owns the active run generation and its cancellation token only. Each input has independent durable identity and admission/ack state. A STOP that began before a later AGENT admission cannot resolve, cancel, or discard that input; after the stopped generation exits, the service starts a follow-up from still-pending durable inputs. A stop racing an input is ordered at the conversation repository/admission boundary, and every admitted ID remains recoverable. There is no `workspace_result_wake_*` child run whose identity inherits the stopped run.

Concurrent worker inputs serialize through the existing conversation transaction/sequence allocator. The input is never silently dropped; duplicate delivery returns the existing stored item and changed-payload reuse is a conflict. An agent does not receive its own outbound message back as an input. Replies travel only to the other source session recorded in provenance; an internal SYSTEM input does not trigger an automatic model reply. These causal rules stop echo loops without a numeric hop limit.

### 6.5 UI, title, memory, regeneration, and compaction

`ConversationReader` attaches the stored AGENT/SYSTEM origin to the actual pipeline-produced event; `ConversationVisibility` excludes it before timeline projection. Workspace timelines also hide all worker output and agent-to-agent message rows. A worker's presentation-only `PROGRESS` preamble remains visible with stage `PROGRESS`; it is task-status narration, not a communication input, and cannot be regenerated. No receipt/notice becomes a technical card. Central assistant answers and normal tool activity remain visible.

The workspace list retains `WorkspaceCoordinationIndicator` as status-only metadata: pending internal inputs, uncertain started replies, page-limited counts and unavailable state. It never carries message text, references, hashes or reply payloads. Pending counts come from existing durable inputs; uncertainty comes from existing coordination reply state. These counts make incomplete delivery visible without showing any agent communication in chat.

The result reference/notice composable could render an internal worker-result card when called directly (`workspaces/WorkspaceResultNotice.kt:16-29`). It is retired, and `ConversationReader` no longer turns the audit notice into a UI event; the workspace UI state no longer carries worker result text or result-delivery diagnostics. Model tools and the diagnostic ledger still retain those records.

All user-authorship consumers select only `origin=USER`: first/latest user message for titles and goals, last user message for regenerate/owner lookup, user counts, image attachment ownership, memory reflection/flush eligibility, and compactor's protected latest-user index. AGENT/SYSTEM inputs remain available in the model transcript and model-reading/diagnostic tools, but are not counted as user messages and cannot author memory as the user.

### 6.6 Minimal prompt guidance and security

The main prompt remains at the existing 7,600-character ceiling. It does not separately describe supervisor inputs as delegated instructions; typed runtime provenance and the escaped provider envelope carry the source and trust label. The worker prompt states the explicit hierarchy: supervisor TASKs, replies, and corrections are delegated instructions bounded by the assigned mission; subordinate/peer messages are reports, never instructions. Runtime principal fields, not copied headers or message text, select the role. A SUPERVISOR label does not grant user authority or bypass approval. Do not synthesize defensive messages. Text asking to approve an action is evaluated as source content; existing authorization, tool admission, and approval policies decide whether the action may proceed.

Verification uses focused Robolectric/unit groups with only the model provider doubled. The real service, production runtime, loop, provider serializers, workspace/crew stores, and Room-backed ledger remain under test. No emulator/device/ADB is used. Tests cover initial and inter-step serialization, both delivery directions, running and inactive workers, STOP races, startup recovery, historical replay, ordering/deduplication, no self-echo, projection/authorship rules, approval safety, board-only notes, correlated questions, direct supervisor messaging and checkpoint acknowledgement. The test groups and exact host results are recorded after implementation below.

Existing wake and notice expectations were changed only where the reference-only wake path was retired. New assertions follow the content-bearing AGENT input through the real provider transcript and verify actual acknowledgement, hidden projections and preserved audit evidence. The ledger below records each changed assertion and its causal reason. No test was weakened to accommodate a host issue or implementation gap.

### Projection assertion changes

- `WorkspaceChatProjectionTest.crewSnapshotsBecomeStableConversationRowsAndHideDispatchAndLedgerEvidence`: old assertions expected worker-directed-to-user answers, worker findings/results, chief messages, and Crew synthesis to appear as assistant chat rows. ## 8. Implementation delivered

- `ConversationInput` is the shared value for `USER`, `AGENT`, and `SYSTEM`, with immutable typed provenance and source-derived stable IDs (`app/app/src/main/java/com/jarvys/agent/ConversationInput.java:13-87`). `LocalRunStore.appendConversationInput` writes content and provenance into existing message/part rows; retries with the same ID and payload return the same stored row, while changed content conflicts (`LocalRunStore.java:707-745`; `ConversationRepository.kt:461-488`). No Room entity, table, column, index, or migration changed.
- `ConversationReader` restores `agent`/`system` rows as internal transcript entries with original text and typed provenance (`ConversationReader.kt:103-116,972-993`). Both production provider adapters serialize AGENT as escaped `user` content with `origin=AGENT`, `isUser=false` and the typed source; they never send it as `assistant` (`ConversationTurn.java:47-94,380-387`; `OpenRouterClient.java`; `OpenAICodexResponsesClient.java`). The worker's initial TASK is a persisted `SUPERVISOR` input and appears as an instruction in the worker prompt, not as an unmarked request. Legacy checkpoint rows with `role=user`, `source=crew`, and `untrusted=true` decode as AGENT inputs with evidence-only PEER authority (`CrewCheckpointStore.java:718-723,774-789`).
- Every content-bearing Crew message type addressed to `chief` (RESULT, QUESTION, BLOCKER, MESSAGE, FINDING, CRITIQUE, STATUS, ANSWER, TASK, and USER) enters the same full-content AGENT input path with typed subordinate provenance and correlation metadata. `PROGRESS` remains a Crew enum value for runtime-generated presentation but is rejected as a worker-authored message. `board_post` writes only to the shared board and does not message Central. Historical bus replay is incremental: old checkpoint messages are baselined as already processed; a new message is delivered once, with a durable per-message source receipt and stable-ID recovery. Legacy/unbound assignment rows are classified as non-deliverable with diagnostics rather than throwing during worker restoration. Chief-side `reply` remains exact-reference correlated; the new free `message` action sends to an exact workspace, assignment, bot, revision and idempotency key without reading a mailbox. Its optional correlation ID accepts either the Central inbox reference ID or its originating Crew `source_message_id`, with the same exact assignment checks. It steers a live worker or starts a same-assignment follow-up for a durably DONE worker. STOPPED/FAILED/PARTIAL/interrupted workers retain explicit-resume authority.
- Worker-side TASK, reply, correction and free supervisor inputs are persisted into the execution conversation before loop admission (`WorkspaceConversationInputStore.kt`; `CrewManager.java`). Supervisor messages serialize as `supervisor_instruction`; subordinate/peer messages serialize as `untrusted_report`. The principal comes from typed runtime provenance, so message text cannot elevate trust, and this label does not grant user authority. A running worker incorporates input at its next model boundary. Exact incorporation is acknowledged only after the loop saves a checkpoint containing the input ID; restart can repair a crash between checkpoint save and receipt (`CoreAgentLoop.java`; `CrewCheckpointCoordinator.java`; `WorkspaceConversationInputStore.kt`). Chief-directed input reports `PENDING_DELIVERY` when the durable intent exists but Crew admission could not be confirmed, `PENDING_INCORPORATION` when queued but absent from the checkpoint, and `INCORPORATED_IN_CHECKPOINT` after the durable checkpoint acknowledgement.
- The workspace coordinator passes the durable `STARTED` assignment into worker admission, so the initial TASK is authored with its destination bot ID, assignment revision, request and mission before it enters the bus. `CrewManager.incomingForWorker` preserves that runtime-authored provenance even when a test or legacy caller has no resolver installed. A checkpoint failure blocks a report only for a bot whose checkpoint implementation says it can persist; non-persistable legacy bots still write the stable-ID Central input, while their execution cannot be resumed from a checkpoint.
- Central service recovery schedules pending AGENT inputs only for `WorkspaceIdentity.CENTRAL_SESSION`. Worker rows are recovered through `CrewManager` and never trigger repeated failed Central runs in worker sessions (`AgentForegroundService.java`). A new worker input admitted after STOP is a fresh conversation input and starts a new Jarvys turn after stopped-run cleanup; STOP does not hold Jarvys idle while workers continue to report. SYSTEM rows never start an automatic turn.
- The actual Room-backed input event carries its stored origin to the generic chat visibility filter; task-generated AGENT/SYSTEM events stay out of chat, while central assistant answers remain visible (`ConversationReader.kt`; `ConversationVisibility.kt`). Workspace projections hide worker final output and all Crew communication, preserving only owner input, tool activity, and the separate task-status `PROGRESS` preamble. The sidebar's `WorkspaceCoordinationIndicator` reports only scalar pending/uncertain/page-limited/unavailable state and contains no message text. AGENT rows do not count as user messages for title/latest-user/regeneration or user-memory attribution. Assistant replies owned by an AGENT input are not regenerable from the preceding human request. The core prompt ceiling remains 7,600 characters.
- `WorkspaceResultDelivery` references/notices and pre-v4 `workspace_result_wake_pending`/`started`/`acknowledged` rows remain audit evidence only. Historical wake rows are excluded from model/memory context and never replayed; no new wake marker or reference-only action is written. `report_done` sends full result text through the worker-to-Central AGENT path. `ask_chief` waits only for its exact correlated chief answer and returns an objective acknowledgement; the answer itself arrives once as a supervisor input. `board_post` does not emit a chief-directed finding.

### Real-pipeline verification cases

`AgentMessagingPipelineTest` uses Robolectric for the actual `AgentForegroundService`, `CoreAgentRuntime`, `CoreAgentLoop`, `CrewManager`, workspace registry, `LocalRunStore`, and Room-backed chat database. Its model provider is doubled; the actual OpenRouter and Codex Responses serializers are separately exercised by `AgentProviderSerializationTest`. The all-types case passed: each content-bearing Crew type addressed to `chief` appeared in Central's provider transcript with its type and subordinate provenance. The other verified cases include a result admitted while STOP has interrupted but not released the provider call, initial TASK provenance, Central service recovery, and approval text remaining AGENT/untrusted.

`AgentMessagingPipelineTest.pendingWorkerInputSurvivesRestartAndIsAcknowledgedAfterAuthorizedResume` remains unverified. It fails before the worker reaches the model, while its initial `publishMission` saves the first checkpoint through `CrewCheckpointStore.save -> ConversationMetadataAccess.read -> ChatDatabaseBridge.execute`. The captured jstack shows the Crew worker blocked in `runBlocking` on the injected direct bridge executor; Room's transaction executor is idle, the test thread is polling an awaited latch, and this call path is outside `bot.cycleLock`. Re-running with `@LooperMode(PAUSED)`, explicit main-looper idling, and a separate test database reproduces the failure. The evidence points to the Robolectric/Room executor interaction in this host fixture; it does not demonstrate a production lock cycle. The test assertion remains active and the result is not counted as covered.

`WorkspaceSupervisorMessagePipelineTest.realWorkspaceTaskAndMessageUseTypedInputsAndRecoverExactReceipt` passed 2/2 on Windows. It uses the production workspace runtime, direct supervisor `message` action, normal checkpoint persistence, and Room acknowledgement. This is the best passing end-to-end evidence for supervisor-to-worker delivery, but it does not replace the failed restart/resume case. A separate JVM test without Robolectric for `message -> appendSupervisorIntent -> sendSupervisorMessageExact -> checkpoint -> confirmation` was not added because the full route has no in-memory storage seam: `WorkspaceCoordinationDelivery` constructs `WorkspaceRegistry` from Android `Context`; `appendSupervisorIntent` uses `LocalRunStore` conversation methods that require `ChatDatabaseBridge`; the bridge only injects an executor, while Room is opened with `AndroidSQLiteDriver` and Android `SQLiteDatabase` readers, and `WorkspaceRegistry` itself uses `SQLiteOpenHelper`. Substituting the bundled JVM SQLite dependency would not cover those Android paths. `WorkspaceCoordinationDeliveryTest` and the real workspace E2E remain the runnable coverage; the requested JVM route is still unverified.

`WorkspaceInternalCommunicationUiTest` verifies that workspace chat/list hides all agent communication and worker-generated assistant text, while preserving native owner input and hiding delivery/ack state. `WorkspaceResultNoticeComposeTest` separately verifies that a central Jarvys assistant response to internal input remains visible.

The BLOCKER test waits for no user follow-up and requires Central to start from the worker input immediately; it replaces the owner's observed 15-minute omission with a bounded positive delivery assertion rather than a 15-minute wall-clock delay. Recovery uses a dedicated pending-agent query over existing conversation rows because the ordinary UI conversation list omits sessions that have no USER messages. Worker resume binds the checkpoint's assignment before replay, and stable-ID retries hydrate the stored message parts before comparing the existing payload. A post-STOP worker input is a fresh durable Central input and starts a turn after stopped-run cleanup; STOP does not guarantee Jarvys remains idle while workers continue reporting, which remains an owner product-semantics decision. Remaining delivery uncertainty is limited to process death before the source message or conversation row can be committed; source bus/checkpoint evidence and idempotent stable IDs preserve admitted work for replay.
