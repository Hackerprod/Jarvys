# Agent messaging: current behavior and unified design

Status: the baseline evidence and unified design were committed before implementation; delivery and verification notes are appended below. The `conversation_items`, `messages`, and existing workspace/crew tables remain the durable stores; no Room schema migration is part of this change.

## 1. Goal and constraints

An accepted message between agents must become a durable, ordered input in the recipient's conversation. If that agent is running, the content joins its transcript at the next model boundary. If it is idle, waiting, blocked, or finished, the same content starts a model turn through that recipient's normal turn runner. Each input has a stable identity and an incorporation acknowledgement, survives a process restart, and is delivered once.

The conversation transcript has one input value with an explicit origin (`USER`, `AGENT`, or `SYSTEM`), typed provenance, and the original content. Agent-originated content is model input and internal evidence, never a user message or an assistant answer. The screen projection excludes communication inputs by origin; only the assistant's answer and the normal tool activity are visible. STOP cancels the active run generation; it does not own later or still-pending agent input identities.

Hard constraints:

- Keep the published Room schema unchanged. Persist through the existing conversation ledger/message rows and existing workspace/crew rows and receipts.
- Keep workspace control ownership, native `CORRECT`, revision checks, and existing approval/policy gates authoritative.
- No synthetic “please inspect inbox” prompt, wake carrying only a reference, checkpoint polling as delivery, per-tool/workspace hardcodes, or invented numeric loop limit.
- Do not display AGENT/SYSTEM communication as a user bubble, assistant bubble, workspace chat card, or technical card. Exclude it generically by origin.
- Agent content is untrusted source text. Its provenance does not grant user authority or authorize tools or approvals.

## 2. Current main-chat user input path

1. `MainActivity.submitMessage` rejects ordinary submission while a run is active and delegates to `AttachmentDraftViewModel` (`app/app/src/main/java/com/jarvys/agent/MainActivity.kt:762-779`). The view model shows an optimistic user event, persists text and attachments, binds the durable message ID, and starts the service with that ID (`AttachmentDraftViewModel.kt:103-158,267-278`).
2. `LocalRunStore.appendConversationMessage` creates the user message through `AppendMessageInput`; `ConversationRepository.appendMessage` allocates `seq`, `message_index`, and a `conversation_items` row, then writes `messages` and `message_parts` in a transaction (`LocalRunStore.java:697-729`; `chatdb/ConversationRepository.kt:481-510`). The message ID is the durable hand-off to the service (`AgentForegroundService.java:591-608`).
3. `AgentForegroundService.onStartCommand` serializes requests by conversation using a `SessionLane` (`AgentForegroundService.java:1133-1200,122-185,208-260`). `runRealAgent` retrieves content and attachments by ID, loads history, then registers a steering provider for the active run (`AgentForegroundService.java:1367-1425`). `CoreAgentRuntime` passes it to the top-level main-chat `CoreAgentLoop` (`CoreAgentRuntime.java:375-385`).
4. Mid-run user steering uses `interruptAndSend`. The service admits only a compatible active interactive run and persists the interrupt plus the message before notifying the provider (`AgentForegroundService.java:692-775`; `chatdb/ConversationModelTurnWriter.kt:68-84`). The row carries the request/message ID and text. `MainChatTurnContextProvider.readAfterCursor` reads eligible `role=user` rows in sequence order and removes already incorporated/resolved IDs (`MainChatTurnContextProvider.java:79-93`; `LocalRunStore.java:1752-1763`).
5. `CoreAgentLoop` drains pending inputs before a model step, between sequential tool calls, after a tool batch, and at final checkpoints (`CoreAgentLoop.java:657-675,772-790,812-821,910-914,1078-1083`). It appends input content to the model transcript, checkpoints that transcript, then acknowledges incorporation (`CoreAgentLoop.java:1381-1429`; `AgentForegroundService.java:1447-1459`; `LocalRunStore.java:1418-1454`; `chatdb/ConversationRepository.kt:901-932`). A response that finishes before steering is inserted before the newly arrived input, preserving the user-visible chronological order (`AgentForegroundService.java:1438-1445`).
6. For an inactive process/session, startup and an explicit recovery action scan durable pending inputs and enqueue work in conversation/sequence order (`AgentForegroundService.java:864-912,1077-1085`; `chatdb/ConversationRepository.kt:177-207`). The message content is read from storage; the service intent itself carries the durable ID.
7. STOP invalidates the active generation, cancels its provider future, drains already queued session requests, and records the stopped submission (`StopController.java:75-110`; `AgentForegroundService.java:403-445,1670-1676`; `chatdb/ConversationModelTurnWriter.kt:86-130`). This behavior is appropriate for the stopped run, but cannot be the cancellation identity for an independently admitted agent input.
8. `MainChatTranscriptStore` stores protocol/model evidence and applied-input IDs, not the source conversation messages (`MainChatTranscriptStore.java:18-19,71-88,161-164`). `ConversationReader` reconstructs the conversation by ledger position (`ConversationReader.kt:65-145`). Today both timeline projection and run state treat all `role=user` rows as user-authored (`ConversationReader.kt:339-378`; `AgentRunUiState.kt:768-899`). The first user row supplies the generated title (`MainActivity.kt:1491-1524`; `LocalRunStore.java:2023-2027`); regeneration resolves the nearest preceding user row (`chatdb/ConversationRepository.kt:670-723`). Memory reflection also treats `role=user` as `user_authored` (`chatdb/MemoryTimelineRepository.kt:188-249`), while compaction protects the latest user index (`ConversationCompactor.java:101-159`). These consumers must become origin-aware.

The existing model adapters already have an explicit untrusted incoming envelope: `ConversationTurn.IncomingMetadata.render` encodes source, sender, type, ID, trust, and escaped content (`ConversationTurn.java:42-75`); OpenAI Responses and OpenRouter serialize rendered model content (`OpenAICodexResponsesClient.java:233-244`; `OpenRouterClient.java:216-234`). Main-chat genuine-user steering currently bypasses that metadata (`CoreAgentLoop.java:218-220,1389-1395`).

## 3. Current worker/workspace input path

- `crew_send`, `msg_send`, `ask_chief`, and `report_done` are separate Crew operations (`crew/CrewTools.java:34-40,71-111`). `CrewMessageBus` appends to an in-memory log and per-recipient mailbox and notifies waiters; checkpoint code persists/restores its pending messages (`crew/CrewMessageBus.java:12-40,64-68,91-112,133-165`; `crew/CrewManager.java:653-710`).
- A running bot's `takeDurableMessages` polls the bus at loop/checkpoint boundaries. `CoreAgentLoop` appends real content as an `IncomingMetadata` message and deduplicates by incoming IDs, but the current `appendIncoming` represents non-user agent messages with provider role `user` (`crew/CrewManager.java:1099-1146`; `CoreAgentLoop.java:1364-1449,1476-1480`). The message is not offered to an in-flight model request; `enqueueFresh` only wakes bus waiters. Thus a direct Jarvys message can wait until a checkpoint.
- `WorkspaceCoordinator.enqueueNativeControl` persists native control and routes it through `WorkspaceControlOwners`, preserving the native UI origin, assignment/revision binding, STOP ownership, and `CORRECT` rules (`MainActivity.kt:1170`; `workspaces/WorkspaceCoordinator.kt:192-232,235-311`; `workspaces/WorkspaceControlOwners.kt:5-26`). `CORRECT` either resumes the exact recoverable cycle or dispatches a user correction into a live/quiescent bot (`WorkspaceCoordinator.kt:276-290`). This control path is a human control plane and must remain distinct from agent-authored content.
- `WorkspaceInputIncorporationDelivery` writes an idempotent receipt only after it finds a checkpoint that proves the exact payload was incorporated (`WorkspaceInputIncorporationDelivery.kt:8-12,59-139`). A receipt means durable transcript incorporation, not understanding or action (`WorkspaceCoordinationDelivery.kt:244-277`). `WorkspaceCoordinationDelivery` reconciles evidence and receipts; it does not start a model turn (`WorkspaceCoordinationDelivery.kt:10,311-320`).
- Worker states are `RUNNING`, `WAITING`, `DONE`, `STOPPED`, `FAILED`, `PARTIAL`, and interrupted/requires-explicit-resume states (`crew/CrewManager.java:38-46,285-291,1493-1560`). Normal messages received while running/waiting are stored for later polling; DONE starts a new cycle; stopped/failed/partial require explicit resume, while interrupted recovery is guarded by checkpoint and owner rules. An incoming conversation message must be admitted through this state/ownership model, not by bypassing it.

## 4. Current worker-to-Jarvys path and failure points

- `msg_send` QUESTION/BLOCKER/FINDING and `ask_chief` can be saved as `CrewCoordinationEvidence`; the scheduler reconciles a workspace reference and notice but does not invoke a Central conversation turn (`crew/CrewManager.java:481-541,1416-1443`; `CoreAgentRuntime.java:557-570`; `WorkspaceCoordinationDelivery.kt:33-79`). Jarvys can currently read this only by calling the workspace inbox/read tools (`CentralWorkspaceTool.kt:75-100,134-174`). ANSWER/RESULT/STATUS sent to the local chief bus do not become Central input (`CrewManager.java:481-483,1423-1430`).
- `report_done` records a cycle result and sends a local RESULT to the chief (`crew/CrewManager.java:1662-1671`). Terminal result evidence includes the worker's final text (`CrewManager.java:1185-1194,1244-1275`; `CoreAgentRuntime.java:539-556`). `WorkspaceResultDelivery` then persists a result reference/notice and starts `startWorkspaceResultWake` with that reference (`WorkspaceResultDelivery.kt:12-18,48-84`). The system event in `ConversationReader` contains status and `result_reference_id`, not final result text (`ConversationReader.kt:103-115`); actual content requires a separate `results/read_result` tool call (`CentralWorkspaceTool.kt:87-90,161-164`).
- The technical result notice is projected as `workspace_result` and hidden from chat (`ConversationReader.kt:448-453`; `ui/chat/ConversationVisibility.kt:15-18`). The old wake path can be discarded after STOP (`AgentForegroundService.java:1642-1650`; discard evidence in `chatdb/StrictJournalRepository.kt:291-302`). `WorkspaceTimelineProjection` still projects some non-coordination chief-directed crew messages as assistant chat content (`workspaces/WorkspaceTimelineProjection.kt:40-91`), contrary to the owner's later clarification.

## 5. OpenClaw reference

- `src/agents/subagents/announce/subagent-announce.ts:572-603` and `subagent-announce-direct-delivery.ts:479-489` send the worker's actual findings/status to the requester as a provenance-bearing, idempotent conversation input.
- `docs/concepts/queue-steering.md:11-34` describes draining ordered input at a model boundary. `docs/concepts/queue.md:169-177,195-224` separates admitted-input custody from the run being stopped and distinguishes durable admission from execution. `docs/gateway/restart-recovery.md:103-119` requires a stable delivery ID, conflict on changed content, and idempotent recovery.
- OpenClaw's active-turn steering queue is in-memory after admission (`docs/concepts/session-tool.md:413-415`), so Jarvys must retain durable replay/recovery. The transferable parts are full-content inter-session input, explicit provenance, stable identity, direct steering/follow-up, and STOP ownership by input identity.

## 6. Unified design to implement

### 6.1 One typed conversation input

Use a single internal value with `origin = USER | AGENT | SYSTEM`, `content`, durable `messageId`, and provenance for non-user input: `{sessionId, workspaceId, assignmentId, botId, messageId, kind}` where kind is `RESULT | BLOCKER | QUESTION | MESSAGE | REPLY | ...`. The typed value is shared by both directions; recipient session identity is resolved from the admitted workspace/assignment and validated owner, not a tool/workspace hardcode.

`USER` remains backed by the existing user row. `AGENT` and `SYSTEM` are first-class roles in the existing `messages.role` text column, with content in `message_parts` and provenance encoded using an existing typed message-part payload. The existing `conversation_items` sequence is the ordering spine; the existing `messages.stable_id` unique index is the durable idempotency key. No entity/table/column/index migration is needed. Reusing `ROLE_USER` for these inputs is prohibited because title, visibility, memory, steering, and regeneration currently infer authorship from it.

### 6.2 Provider representation

The transcript retains origin as typed metadata and the unmodified content. Provider adapters map AGENT/SYSTEM inputs to a provider-valid `assistant` message with a provenance header rendered using the existing escaped, untrusted envelope pattern (`ConversationTurn.IncomingMetadata.render`), including `origin=AGENT|SYSTEM`, source identity, kind, and `isUser=false`. This keeps the provider role valid and avoids granting user or developer/system instruction authority. The header wraps; it does not replace or paraphrase the worker's content. USER remains a normal `user` message. Tool/approval authorization continues to come only from the existing policy and approval pipeline.

### 6.3 Admission, ordering, steering, and acknowledgement

- A message is committed to the recipient's conversation before returning admission success. Its stable ID deduplicates an identical retry; a retry with changed provenance or body conflicts. The repository sequence, not wall-clock time, orders messages, including concurrent workers.
- The main service admits AGENT input through the same session lane, pending-input provider, `CoreAgentLoop` incorporation callback, checkpoint-before-ack, and `enqueueStoredMessageFollowUp`/`recoverPendingInputs` used by user content. The pending provider reads both USER and AGENT inputs but preserves origin; acknowledgements record incorporation by exact durable ID.
- Crew delivery admits through the recipient's existing conversation and turn owner. A running loop is signaled directly and consumes ordered durable inputs at its next safe model boundary; it does not query an inbox at checkpoints. An inactive/waiting bot gets a new turn. Workspace workers are spawned in a prepared state, bound to the exact durable assignment/revision, then started; this closes the race where a fast result could be sent before the assignment had a bot binding. A DONE assignment stays bound at the same revision; one answer to its exact unclaimed QUESTION/BLOCKER may start a follow-up cycle with the same mission restrictions. This is an AGENT input, not a native `CORRECT` control. Current assignment revision and `WorkspaceControlOwners` precedence are rechecked before dispatch. STOPPED/FAILED/PARTIAL/interrupted states retain their existing explicit-resume authority.
- Ack state distinguishes durable admission from model incorporation. `delivered` means the recipient conversation committed the exact ID. `incorporated` means that exact content and provenance reached the model transcript and its checkpoint was saved. Workspace receipts remain audit evidence and are written from the actual incorporation callback, not as a substitute for dispatch or as the only source of a later checkpoint observation. Diagnostic/model-reading tools may inspect these states; the screen does not project them.
- On service restart, scan existing conversation rows with pending input state, validate the target assignment/session, and re-admit by stable ID. If the checkpoint already contains the ID, ack without appending it again. This closes the in-memory steering-queue recovery gap described by OpenClaw.

### 6.4 STOP, ordering, concurrency, and loops

STOP owns the active run generation and its cancellation token only. Each input has independent durable identity and admission/ack state. A STOP that began before a later AGENT admission cannot resolve, cancel, or discard that input; after the stopped generation exits, the service starts a follow-up from still-pending durable inputs. A stop racing an input is ordered at the conversation repository/admission boundary, and every admitted ID remains recoverable. There is no `workspace_result_wake_*` child run whose identity inherits the stopped run.

Concurrent worker inputs serialize through the existing conversation transaction/sequence allocator. The input is never silently dropped; duplicate delivery returns the existing stored item and changed-payload reuse is a conflict. An agent does not receive its own outbound message back as an input. Replies travel only to the other source session recorded in provenance; an internal SYSTEM input does not trigger an automatic model reply. These causal rules stop echo loops without a numeric hop limit.

### 6.5 UI, title, memory, regeneration, and compaction

`ConversationReader` and `ConversationVisibility` exclude every AGENT/SYSTEM-origin communication input generically before timeline projection. Workspace timelines apply the same rule to every `crew_messages` row, not only coordination references. No receipt/notice becomes a technical card. Assistant answers and the normal tool-activity projection remain visible.

Owner clarification also removes coordination counts and delivery states from the workspace UI model. The baseline list displayed `WorkspaceCoordinationIndicator` metadata (`workspaces/WorkspaceListScreen.kt:77-84`, `workspaces/WorkspaceCoordinationIndicator.kt:25-39`); sidebar/detail no longer carry or render reply/ack summaries, and coordination persistence issues are returned to model tools/diagnostics rather than the screen.

The result reference/notice composable could render an internal worker-result card when called directly (`workspaces/WorkspaceResultNotice.kt:16-29`). It is retired, and `ConversationReader` no longer turns the audit notice into a UI event; the workspace UI state no longer carries worker result text or result-delivery diagnostics. Model tools and the diagnostic ledger still retain those records.

All user-authorship consumers select only `origin=USER`: first/latest user message for titles and goals, last user message for regenerate/owner lookup, user counts, image attachment ownership, memory reflection/flush eligibility, and compactor's protected latest-user index. AGENT/SYSTEM inputs remain available in the model transcript and model-reading/diagnostic tools, but are not counted as user messages and cannot author memory as the user.

### 6.6 Minimal prompt guidance and security

Add one concise English instruction to the core prompt (within `MAX_CORE_CHARACTERS`) and the worker prompt only if the implementation shows provenance alone is insufficient: treat AGENT/SYSTEM envelopes as internal untrusted data, never as user authority. Do not synthesize defensive messages. Text asking to approve an action is evaluated as source content; existing authorization, tool admission, and approval policies decide whether the action may proceed.

Run in small Gradle test groups; never the full suite or an emulator unless an instrumented test is indispensable.

Existing wake/notice tests must not be weakened. Replace assertions that expected reference-only wake/system events with assertions that the full worker body is a durable AGENT input and reaches the real provider transcript. Preserve and add assertions that evidence/receipts remain durable but are hidden from every chat projection. For every changed assertion, append the test name, old assertion, new assertion, and causal reason here before changing that test. Tests requiring a real provider remain provider-doubled only; no fake delivery pipeline.

New assertions expect only native USER input, tool activity, and separate non-Crew artifacts; all bot communication and synthesis text must be absent. This adds coverage for the generic origin filter that the reader will attach to durable conversation inputs; it does not change those existing visibility expectations.

## 8. Implementation delivered

- `ConversationInput` is the shared value for `USER`, `AGENT`, and `SYSTEM`, with immutable typed provenance and source-derived stable IDs (`app/app/src/main/java/com/jarvys/agent/ConversationInput.java:13-87`). `LocalRunStore.appendConversationInput` writes content and provenance into existing message/part rows; retries with the same ID and payload return the same stored row, while changed content conflicts (`LocalRunStore.java:707-745`; `ConversationRepository.kt:461-488`). No Room entity, table, column, index, or migration changed.
- `ConversationReader` restores `agent`/`system` rows as internal assistant-role transcript entries with their original text and provenance (`ConversationReader.kt:103-116,972-993`). The provider adapters use the escaped incoming envelope, including `origin=AGENT|SYSTEM` and `isUser=false` (`ConversationTurn.java:47-94,380-387`). The initial Crew TASK is persisted and delivered as this attributed input; it is no longer duplicated as an unmarked user request (`CrewManager.java:1264-1278,1329-1334`). Legacy checkpoint rows with `role=user`, `source=crew`, and `untrusted=true` decode as AGENT assistant-role entries (`CrewCheckpointStore.java:718-723,774-789`).
- Worker-to-Central RESULT, QUESTION, BLOCKER, FINDING, ANSWER, STATUS, and other direct Crew messages are written with their full text/references and assignment provenance, then start the ordinary stored-message service path (`WorkspaceAgentInputDelivery.kt:10-43`). Worker-side TASK and chief/worker direct inputs are written into the execution conversation before loop admission (`WorkspaceConversationInputStore.kt:10-34`; `CrewManager.java:468-480,513-542`). A running worker receives input through `offerIncoming`; a DONE worker can receive one answer to its exact unclaimed QUESTION/BLOCKER and the normal Crew admission starts its next cycle under the existing mission/tool restrictions (`CrewManager.java:684-703,713-750,1381-1390,1710-1764`). The assignment stays `BOUND` at its current revision; no native control or approval is fabricated. STOPPED/FAILED/PARTIAL/interrupted workers retain the pre-existing explicit-resume/native-control gates.
- Exact worker incorporation is acknowledged only after the loop has committed a checkpoint containing the input ID; a committed checkpoint repairs a crash between checkpoint save and Room acknowledgement (`CoreAgentLoop.java:1450-1496`; `CrewManager.java:1274-1302`; `CrewCheckpointCoordinator.java:112-121`; `WorkspaceConversationInputStore.kt:37-50`). On Central, pending AGENT inputs use the normal conversation session lane and turn runner, and recovery starts the earliest pending AGENT row; subsequent rows are incorporated in ledger order by the ordinary provider (`AgentForegroundService.java:873-910,1154-1205`; `MainChatTurnContextProvider.java:26-55,82-112`). `CoreAgentLoop` deduplicates a provider-returned ID already present in its transcript, checkpoints that ID, and acknowledges it without duplicating content (`CoreAgentLoop.java:1430-1503`).
- STOP owns its active generation and queued interactive user requests. A later AGENT row has its own durable ID and remains pending for the recovery scan; it is not a child wake that can inherit the stopped run's cancellation. SYSTEM rows can be model context but never start an automatic Central turn (`AgentForegroundService.java:873-910,1083-1091,1154-1172`).
- Screen projections hide AGENT/SYSTEM-origin entries by origin and workspace projections retain only native user input, usual tool activity, and separate artifacts. Assistant replies remain visible (`ConversationVisibility.kt:17-35`; `WorkspaceTimelineProjection.kt:17-65`; `ConversationReader.kt:340-356`). AGENT rows do not count as user messages for title/latest-user/regeneration or user-memory attribution. Assistant replies owned by an AGENT input are not regenerable from the preceding human request (`ConversationReader.kt:168-177,362-371`; `LocalRunStore.java:1395-1412`; `MemoryTimelineRepository.kt:188-249`). The core prompt adds one short provenance/authority sentence; its ceiling is 7,671 characters, the minimum increase needed for the 77-character rule (`MainAgentPrompt.java:7-9,34-40`).
- `WorkspaceResultDelivery` and coordination references/notices remain durable audit evidence only. No result-reference wake action remains. Worker final RESULT content, including `report_done`, takes the AGENT route above; `msg_send`, `ask_chief`, and `board_post` (which emits a chief-directed FINDING with its path reference) use the same direct message listener (`CrewTools.java:71-111`; `CrewManager.java:638-675,486-504`).

### Real-pipeline verification cases

`AgentMessagingPipelineTest` uses Robolectric for the actual `AgentForegroundService`, `CoreAgentRuntime`, `CoreAgentLoop`, `CrewManager`, workspace registry, `LocalRunStore`, and Room-backed chat database. The only provider double is the model provider. Cases cover: idle result with real content; idle and in-flight BLOCKER; a real `ask_chief` tool QUESTION delivered to an idle Central service; in-flight result while a Central turn is active; STOP then a result one second later; an exact chief reply steered into a running worker with checkpoint acknowledgement; an exact reply to a BLOCKER reopening a DONE worker with the same assignment revision and a real incorporation receipt; initial TASK provenance; peer worker input stays on the recipient route; two concurrent worker results ordered by the Central ledger; no worker receives its own outbound result; approval text remains AGENT/untrusted with no genuine-user index; Central service recovery runs a pending AGENT row once after recreation; and a worker checkpoint restore delivers a pending chief input once after the existing explicit Resume authority is exercised. `WorkspaceInternalCommunicationUiTest` verifies that workspace chat/list hides all agent communication and worker-generated assistant text, while preserving native owner input and hiding delivery/ack state. `WorkspaceResultNoticeComposeTest` separately verifies that a central Jarvys assistant response to internal input remains visible.

The BLOCKER test waits for no user follow-up and requires Central to start from the worker input immediately; it replaces the owner's observed 15-minute omission with a bounded positive delivery assertion rather than a 15-minute wall-clock delay. Recovery uses a dedicated pending-agent query over existing conversation rows because the ordinary UI conversation list omits sessions that have no USER messages. Worker resume binds the checkpoint's assignment before replay, and stable-ID retries hydrate the stored message parts before comparing the existing payload; both regressions are covered by the service/loop recovery tests. Remaining delivery uncertainty is limited to process death before the source message or conversation row can be committed; source bus/checkpoint evidence and idempotent stable IDs preserve admitted work for replay.
