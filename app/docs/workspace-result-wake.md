# Workspace result wake for Central

## Before and after

Crew persists immutable terminal output in its execution conversation as `crew_result_evidence`. `WorkspaceResultDelivery.reconcile` binds that evidence to the live workspace assignment, writes the source `workspace_result_reference`, then records `workspace_result_notice` in Central. The old notice path ended by updating `AgentRunUiState` and `WorkspaceChanges`; it did not enqueue a Central model run. The owner therefore saw the technical notice while the agent stayed idle.

On the first insertion, the notice and a `workspace_result_wake_pending` marker commit together in `StrictJournalRepository.appendWorkspaceResultNoticeAndWake`. The marker contains only the validated reference ID. `WorkspaceResultDelivery.notice` asks `AgentForegroundService` to start a system-origin Central turn with that ID when the marker is pending and unacknowledged. The service's existing per-session FIFO lane queues the request behind any active Central run. When the lane takes it, the service transactionally appends `workspace_result_wake_started` after checking that the matching reference remains pending. It does not interrupt or replace the active run.

`ConversationReader.loadConversationContext` projects pending notices into typed `ConversationTurn.Kind.SYSTEM_EVENT` turns with role `system`. The event states the workspace ID, assignment ID, worker-reported terminal state and result reference ID. It contains no raw result text, hash, or worker instructions. Its typed reference ID is carried separately on the turn. `CoreAgentLoop` sends that system turn as model context without creating a user message. Each provider response checkpoint carries only the event reference IDs included in that request. This includes a provider response that requests tools: the tool-call transcript and wake acknowledgement commit together before those tools execute. `MainChatTranscriptStore` persists the transcript rows and acknowledgement in one Room transaction. A duplicate queue item then fails its pending claim and becomes a no-op.

## Durable recovery and delivery semantics

The pending marker remains durable until the first provider response checkpoint containing the event and `workspace_result_wake_acknowledged` commit together. A `started` marker does not consume or hide the pending event. If the process dies or the provider fails before that checkpoint, the event remains pending; another process may retry it. A same-process attempt gate prevents repeated provider attempts until process recreation. Recovery runs at two concrete entry points: `AgentForegroundService.onCreate` calls `WorkspaceResultDelivery.scheduleCatalog`, which enumerates the workspace registry and enqueues each execution session for `WorkspaceResultDelivery.reconcile`; `MainActivity.onResume` calls the same catalog scan. Reconciliation retries a wake only when its durable pending marker exists and is unacknowledged. It never repairs a missing marker on an existing notice: notices already recorded before this behavior was introduced remain historical and do not wake Central retroactively. A newly arriving `ACTION_WORKSPACE_RESULT_WAKE` also starts the service directly. A same-process request set coalesces duplicate intents, while the atomic checkpoint acknowledgement prevents another wake attempt after the first response checkpoint was durably recorded.

The notice and pending marker are written in one Room transaction, so a process death cannot commit only one of those two rows. The worker evidence and source reference are validated before either is disclosed. Wake markers and notices remain excluded from memory input and model-transcript row indexing; the system event is projected only while its exact reference is pending.

The durable local boundary is idempotent: once the first provider response checkpoint commits, the same result cannot enqueue another wake, including after process recreation. If the process dies before that checkpoint, the pending event is retried. Exactly-once execution at the external provider boundary cannot be guaranteed: a process may die after submitting a request but before saving its response, so recovery can submit that ambiguous request again. After acknowledgement, a provider failure or partial turn writes one ordinary visible assistant failure message and does not retry the wake, since replay could repeat tool effects. The checkpoint for a tool-call response is written before dispatch, so a process crash after that acknowledgement but before tool execution or a final answer can leave no failure bubble; the wake still does not retry. If Android force-stops the app or never starts the app/service again after process death, a pending event waits until the next service or activity entry point; the app does not promise a background relaunch. The system does not replay a worker or trust its reported state as verified.

## Chat visibility and evidence

`workspace_result_notice` remains in the durable Central timeline and remains readable through the existing workspace result APIs. It continues to be available to recovery and strict-journal inspection. `ConversationVisibility` filters the generic `workspace_result` timeline event from the owner-facing central chat projection, so UUIDs and audit wording are not shown as a chat card. Crew and workspace result views keep their existing cards.

The model receives only the reference metadata event. It must use the existing `workspaces` tool and `read_result` flow to inspect exact saved output. Tool disclosures continue to describe worker output as unverified evidence; neither the result status nor receipt existence proves that a correction was applied or consumed.

`read_result` may create a missing local notice while the current turn is already inspecting that reference, but it does not create a second wake marker or start a nested turn. A wake turn keeps its own logical owner identity, `workspace-wake:<reference-id>`, on the existing transcript owner fields. Provider output items, tool calls/results and related rows use that owner instead of borrowing the latest user message. Editing or regenerating that earlier user turn therefore does not erase wake work. The wake answer has no user-message owner to regenerate from, so the UI hides its regenerate action and the repository rejects that request rather than replaying an unrelated prompt. No schema or migration was added.

The wake receives the exact `originalUserRequest` persisted on its bound assignment after validating the workspace owner, execution session, assignment state, request ID, mission ID and bot ID. If the workspace or assignment no longer exists, its original request is empty; it never borrows the latest Central message, which may be unrelated. Mutating workspace actions then fail their existing provenance checks, while the model can still read and report. This preserves the existing checks for `create`, `delegate`, `deliver` and `reply`; the wake event itself does not invent or append a user message. The event marks the reported result as a fact to inspect, not verified evidence or permission.

## Stop, provider failure and Android deferral

An explicit user STOP writes `workspace_result_wake_discarded` and removes that event from pending context. Reconciliation and later service starts do not revive it. A provider failure, timeout or partial response before the first response checkpoint leaves the durable event pending, writes no assistant bubble, and permits one provider attempt for that reference in the current app process. The next process start can reconsider it. A failure after a checkpoint has acknowledged the event writes one visible assistant failure message; the event is no longer pending and the wake is not retried. This phase-based boundary prevents both repeated bubbles on pre-checkpoint outages and automatic replay after a checkpoint may have preceded tool effects. User messages queued during the wake go through normal pending-input recovery after the wake exits, whether it completed or failed; STOP resolves them with the existing stopped-input policy. A multi-session recovery scan preserves its durable request order.

On Android 12 and later, a background foreground-service start rejection is treated as a deferral: the pending marker remains, the same-process request and attempt gates are cleared, and the start failure is quiet. A later entry point such as `MainActivity.onResume` can retry once in the same process. The catalog scan is invoked only from app/service entry points, so this does not form a retry loop. The wake is queued on the interactive Central lane, which participates in the existing `BackgroundRunController` lifecycle used by proactive and scheduled runs. The current implementation adds no dedicated result notification while the app is in the background; that notification decision remains with the owner.

Devices that ran commit `d7eaf73` may already have durable wake markers for older result notices. They can wake Central once when this recovery path first runs. Commit `d7eaf73` was not deployed beyond local tests, so no external installation is expected to have those markers.

The Central generic chat renderer intentionally does not show `workspace_result` notice cards. The durable result remains available through workspace result views and APIs. Compaction currently protects the complete transcript suffix beginning at a system event. Narrowing that to protect only the event would require compaction to preserve order while storing a summary of later wake work after that event; the current single-prefix summary cannot represent that safely, so wake work after the event stays protected for this release.

## State and owner policy

Only the persisted terminal states accepted by `WorkspaceResultReference` create wakes: `DONE`, `PARTIAL`, `FAILED` and `STOPPED`. Intermediate Crew states do not create result references and therefore cannot enqueue a wake. Failed and stopped terminal results are delivered so Central can report them.

There is no separate autonomous-wake toggle. An unset action policy defaults to `ALLOW`; an explicit `ASK` or `DENY` remains authoritative for each tool action the model attempts. The wake itself grants no tool permission and bypasses no Android permission. The wake creates no separate user notification; the foreground service uses its existing run notification. Notification permission does not change the durable pending/ack state.

## Files and boundaries

This change uses existing `conversation_items` ledger rows and does not alter Room v1 entities, tables, or migrations. Workspace and Crew UI cards are unchanged. Recovery depends on Android allowing a later service or activity start so the documented scan can run; process, battery, foreground-service and provider limits still apply.
