# Factory app runtime follow-up

This note records the Pulso Ping validation findings, the bridge diagnostic changes, the host-dependency boundary, and what preview evidence can establish. Room schema 1 is unchanged. A runtime change ships only with newly built APKs: generated APKs embed the template DEX and do not inherit changes from a Jarvys update.

## Typed bridge errors

`DatabaseRequest.validate` accepts `createTable.columns` as a JSON object mapping each column name to `{type, nullable}`. It does not accept an array of `{name, type, nullable}` records. The old message hid the failing path. The database validator now reports a stable method/field path and expectation while preserving `INVALID_ARGUMENT` and the same closed grammar, identifier rules, byte limits, quotas and mutation semantics. It never echoes submitted values or unknown field names.

Storage, HTTP request/transfer and notification validation now identify the relevant argument field for common type, range, identifier and text-bound failures. `FactoryConfig.exactKeys` reports the operation's allowed field names without repeating an undeclared input key. `BridgeProtocol` reports the known method when an argument has an invalid JSON shape. Error codes and admission behavior are unchanged.

The new fixed-message/no-value-echo assertions cover these validator paths:

## Compatibility and identity digests

`runtime.info.nativeOperationsPolicy` remains available with its legacy value `host_allow_ask_deny` so generated apps that read the field keep working. New code also reports `nativeOperationsAuthorization=declared_capability_and_android_permissions`. Schema 1 and bridge protocol 1 are unchanged.

`NativeInstalledSource.apkSha256` is the host-reported APK byte hash when `describe` asks Jarvys for an authenticated installed source. For `describeLocal`, it is a local identity digest: SHA-256 of `factory-local-app-v1\n`, package name, signer-certificate SHA-256, version code, and SHA-256 of the packaged config, separated by newlines. It does not claim to hash the APK bytes; `NativeInstalledSourceTest.localSourceUsesInstalledPackageAndPackagedBudgetsWithoutHostCall` checks this exact derivation.

`NativeBackgroundAuthorization.acquire` and `acquireFiniteHttpJob` had no production callers after generated-app background effects moved to local installed identity and authority, so the dead acquisition path was removed. `SourceIdentity` and its strict parser remain because the host-side `FactoryOperationAuthorizationProvider` still uses that wire shape for receipt-bound host operations.
## Host leases and generated-app independence

`NativeOperationSessions.authorize` is the foreground path that contacts `content://<documentBroker>.factory.operations`; `Lease.check` also checks that Binder client before each protected effect. A Binder death therefore ended `notifications.channel` even though the channel belongs to the generated app. This is source/capability authentication, not an approval prompt. Local authorization removes that process dependency only for app-owned effects; it retains operation capability checks, current-page ownership, platform grants, technical budgets and cancellation.

| Boundary | Operations and evidence | Runtime rule |
| --- | --- | --- |
| Generated-app effects | Foreground HTTP/ICMP, Bluetooth, NFC, notifications (including channel/status/show/cancel/permission), speech/TTS, voice recognition, biometrics, location, steps, sensors, recording, app-local secrets, `incomingShare.*`, and haptics use generated-app data or Android APIs (`NativeEffects`, `NativeBleEffects`, `SecretEffects`, `IncomingShareInbox`). Widgets, finite HTTP jobs and scheduled notification delivery are also app-owned when the Activity is absent. | Check the packaged capability and current page in process for foreground effects. Background services derive identity from the Android-installed signer, package version and packaged `factory-app.json` budgets (`NativeInstalledSource.describeLocal`). Android still controls runtime permissions, URI grants, alarms, job scheduling and delivery. Keep network, data, sampling, capture, and cancellation limits. |
| Host-owned resources and handoffs | `documents.*`, file/photo/audio broker transfers, `share.text`, `share.file`, `export.text`, clipboard writes, backup review/commit, and contacts/calendar/phone/maps/browser host activities use pinned host authentication for broker access or external handoff. | Retain pinned package/certificate/UID checks, Binder endpoint authentication, exact capability scope, and Android URI grants. If acquisition fails, report that Jarvys must be installed and active; retry after the host returns before an external effect begins. Never replay an uncertain write, delivery, or commit. |

Clipboard writes remain on the host path because `FactoryClipboardActivity` verifies the generated caller against retained signed scope, checks its live Binder control immediately before writing, marks the clip sensitive on Android 13+, and runs under a secure window. This is a host-mediated privacy boundary around a shared system clipboard, not access to generated-app local state.

`share.text` and `export.text` are text-only Android chooser/picker handoffs in `FactoryRuntime`; each acquires a pinned host lease before launching the Android UI. `export.text` writes through the URI grant Android returns. Binary `documents.*` handles, file sharing and selected-table backups use Jarvys broker flows and their pinned host checks.

An ambiguous host UID fails closed before a file/audio snapshot or external handoff reaches the host. It returns `SOURCE_UNAVAILABLE` with the actionable Jarvys-installed-and-active message; the audio and file-sharing tests assert both that message and that no host activity launches. Package, certificate, UID and endpoint checks remain in place.

The operation list above is an effect boundary, not a relaxation of Android security. `POST_NOTIFICATIONS`, location, microphone, activity recognition, Bluetooth, NFC, document URI grants, and other platform permissions remain controlled by Android. A permission denial remains a denial. Already-sent network bytes, emitted sound, posted notifications, committed data and recipient copies cannot be recalled.

## Preview execution and evidence

`preview` verifies the exact same-project build receipt and APK hash, extracts the immutable built assets, then launches `FactoryPreviewActivity` with a process-local one-shot token. The Activity constructs the same `FactoryRuntime` in a private WebView and serves `www/index.html` plus its project JavaScript from the verified snapshot. It is real project JavaScript and the shared bridge/handlers, with isolated RAM SQLite/storage and simulated external effects. It is not the installed APK process, Android permission acceptance, durable storage, or a live-network certification.

The WebView client already records `page:started` and `page:finished`; the bridge records method request and outcome counts. `preview` returns `launch_requested` immediately because Activity creation and page callbacks are asynchronous. A caller can then use `preview_status`, which revalidates project scope and the exact artifact and returns the retained process-local receipt. `test` remains a synthetic contract suite: it does not load project JavaScript.

The status receipt originally kept only aggregate operation/outcome counts. Validator failures were returned to project JavaScript but were not retained as method/code/message evidence. The pilot adds compact `INVALID_ARGUMENT` validation evidence to `preview_status`: one latest message and a saturating count per known bridge method. These messages come from validators and omit submitted values. This is enough to expose the database schema-shape failure after the page runs, without collecting console strings, request arguments, storage contents, or screenshots. The pilot is a small callback and bounded receipt change; it uses the existing session lifecycle and has low implementation cost and risk.

Console diagnostics are a separate step. The WebView has no `WebChromeClient.onConsoleMessage` collection today. Capturing those messages or JavaScript exceptions could retain user-entered values, URLs or secrets; filtering and lifecycle handling add moderate implementation and privacy risk. A later opt-in stage should collect only for the exact preview during a bounded load window of N seconds, sanitize text, and test expiry on close, reset, pause, replacement and cancellation. N is not set by the pilot and should be chosen before that stage. A page callback is not proof that application initialization succeeded; the agent must poll `preview_status` after `page:started` and report the actual validation errors it sees. A page finish without a recorded error is not a visual or runtime certification.


## Background authorization coverage boundary

The current tests verify the exact local identity digest (`NativeInstalledSourceTest.localSourceUsesInstalledPackageAndPackagedBudgetsWithoutHostCall`), scheduled-job constraints including `replayPossible=false` (`NativeFiniteHttpAuthorizationTest.scheduledJobsCannotClaimReplayOrUnboundedTime`), and foreground notification schedule state transitions (`NativeNotificationEffectsTest`). They do not exercise a cold-process end-to-end delivery through `FactoryHttpJobServices`, `FactoryWidgetReceiverWork`/`FactoryWidgetServices`, or `NotificationInstalledEnvironment.resolve` into the final Android effect. Keep that gap explicit until those receiver/service routes have direct platform tests; the current parser and foreground tests do not certify those delivery paths.

## Rebuild and evidence limits

`factory-runtime-core` changes affect only APKs built from a template containing that DEX. Existing generated APKs keep their embedded older runtime and must be rebuilt and re-signed to receive the fixes. Schema 1 and the bridge protocol version remain unchanged; the preview receipt only gains diagnostic data. Host tests validate the shared runtime and preview registry but do not replace execution of the project's JS on a physical device.
