## Discrepancias documento-vs-codigo y decisiones
1. Doc 4.3: "mover las comprobaciones por id a RunKind" (DeliverFileTool, CodexImage..., BotCreationTool, BotCatalogTool, BotMascotTool, WorkspaceTools, ConnectorArtifactAccess). Resultado de leerlas: solo restringian los turnos de respuesta dentro de las sesiones retiradas; los runs de fondo no pasan por ellas (tareas: `unattendedAccess()==EXCLUDED` y registro por alcance; proactivo: registro propio solo-lectura). Con las sesiones fuera, se eliminan (no se anade fontaneria de RunKind a 8 herramientas sin efecto). RunKind si gobierna lo que tenia comportamiento real: kind de contexto/perfil, `mainChat`, prompt de instrucciones y escritura de `agent_session_state.kind`. Si el dueno quiere RunKind tambien en las herramientas es un cambio aditivo.
2. Doc 4.3 "los mensajes del hilo": se recupera el aviso respondido y su intercambio (hasta el siguiente aviso o la respuesta), no todo el hilo. Motivo: el hilo `task:<id>` acumula todas las ejecuciones de una tarea y recuperarlo entero seria no acotado; la delimitacion es por semantica (un intercambio) y no por un numero.
3. Doc 4.3 pide que la respuesta lleve `proactive_reply_to_message_id`/`proactive_thread_key`: las respuestas por chip ya lo llevaban; la respuesta inline no tiene notice id (se resuelve al ultimo aviso del hilo) y la de tareas ahora lo lleva (antes se guardaba sin hilo, con lo que el referente era imposible).
4. `TaskActionReceiver`: la respuesta rapida de una notificacion de tarea ya no es un mensaje sin hilo en `jarvys-tasks`; ahora es respuesta de hilo `task:<id>` en Central. `ProactiveInteractionDispatcher.refreshNotification` ignora hilos de tarea (TaskNotifier nunca refresco tras una respuesta; se conserva ese comportamiento).
5. `EXTRA_OPEN_PROACTIVE_MESSAGE_ID` se reutiliza para tareas (el nombre es de proactivo; el mecanismo del ancla es generico). No se renombro para no tocar MainActivity/tests de S1/S2.
6. `AgentForegroundService.java:1797` ya etiqueta con el hilo la respuesta del asistente (sin cambios necesarios): la respuesta a un aviso hereda `proactive_thread_key`.
7. `readConversationTimeline` (LocalRunStore/ConversationReader/Bridge) queda sin llamadores de produccion pero se conserva: ~20 tests de timeline lo usan como API de lectura. Candidato a S8.
