## Meaning and authority

An immutable input binding refers to an existing central reply intent or an admitted native CORRECT control. It binds the original source payload, mailbox identity, assignment/mission/bot and admission cycle. Native corrections preserve exact text and user provenance; replies remain untrusted chief data. Generic Crew messages and legacy checkpoints remain compatible. Missing legacy cycle identity yields no invented incorporation proof.

The worker records evidence only when it appends the exact incoming turn or the exact answer batch returned by that ask_chief invocation. Source, actual delivery and transport hashes are separate. The first incorporation cycle survives later checkpoints and compaction. Applied mailbox IDs alone, sanitized historical copies and in-memory checkpoints are insufficient.

A local reconciliation validates the current checkpoint envelope and project identity, syncs the same opened file and directory chain, then records the exact serialized payload digest. This proves durability confirmation of the observed checkpoint, not that the original save returned successfully or that this was the first checkpoint ever written. Missing project state is never recreated to obtain a receipt. Physical power-loss behavior remains unverified.

## Independent receipt

The existing Central ledger stores one immutable receipt per stable source identity. Different source/body/mailbox/cycle bindings conflict. A later supporting checkpoint alone does not replace the first receipt. Existing reply and native-control dispatch states remain unchanged: an uncertain dispatch can coexist with a proven historical incorporation.

No model call, input resend, worker restart or effect replay occurs during receipt reconciliation. A successful checkpoint callback only signals the existing finite local receipt scheduler. Receipt failures leave evidence available for later reconciliation and do not pretend an external action failed.

Current owner, source, deletion and READ policy govern disclosure. Automatic reconciliation uses ALLOW. An authorized foreground read_message under ASK can reconcile only its exact reply; that approval cannot acknowledge other replies or native corrections. DENY and STOP remain effective at admission boundaries. Native correction metadata is shown only under current permitted reads.
